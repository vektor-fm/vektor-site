The Teardown · 004

One prompt, two racks,
no winner.

Jensen Huang posted that AGI has arrived. The film gave GPT-6 Pro and Fable 5.1 the same prompt and a clock, and then refused to name a winner. That refusal was the product. This is the rig that made it defensible, and the part of it you can install.

Fig. 01 ·

the line the clock sits on the wrong side of

Everything above the line belongs to the vendor: their system prompt, their tools, their search, their timer. Everything below it is ours and identical for both files. The two elapsed times were measured above the line. That is why the film says "in under fifteen minutes each" and never says which was faster.[1]

Fig. 02 ·

the prompt, frozen before either answer existed

The whole test is one message, sent once to each product, with no follow-ups and no hand edits to whatever came back. The message was hashed before either run started, and both run records carry the hash, so nobody can quietly tune the wording after seeing the first result.[1]

Build an interactive exploded-view 3D diagram of an NVIDIA GB200 NVL72 rack
(Grace Blackwell) in three.js, as a single self-contained index.html that
loads three.js from a CDN. Requirements: the rack's main parts modelled as
simple 3D geometry and labelled (compute trays with Grace CPUs and Blackwell
GPUs, NVLink switch trays, power shelves, the NVLink spine and cabling,
liquid-cooling manifolds, the rack frame); an explode/assemble slider that
spreads the parts apart along sensible axes; an orbit camera; click any part
to show its name and a one-line description. Make it look premium. Return
only the complete file.

sha256 3ad96c0abdab9c461474be08f0b6398a29745630cbc0f888fb752f36d901ef0d

Two things in it are deliberate. "Simple 3D geometry" means a schematic rack is the spec, so a simplification cannot later be counted as a defect. And "return only the complete file" means the first artifact is the one that gets judged, unrepaired. A broken CDN import or a dead slider is a result, not an environment problem to be fixed before scoring.[1]

The protocol was written before either output was available. It says, in its own words, that this is "a disclosed product demonstration, not an isolated model benchmark," because the two products add their own system instructions, tools and reasoning settings and none of that can be equalised from outside.[1] The Claude side ran in safe mode with tools off, which disables the repository's own instruction files, skills and hooks. That step exists for an uncomfortable reason: this repository contains the film's desired verdict, and a normal session would have read it.

Fig. 03 ·

below the line: the same fifteen steps, twice

Once a file exists, the vendor is out of the loop and the test becomes a script. The same headless Chrome, version 145.0.7632.77 with software WebGL, serves each file from a local port and runs the same sequence: load and wait five seconds, screenshot; slider to 50 percent, to 100, back to 0, screenshot each; drag the canvas 320 pixels twice and back 640, screenshot each; slider to 100 and click five fixed fractions of the canvas, screenshot each. Then the same again at a portrait viewport of 1080 by 1920, because a layout that only works on a desktop monitor is not the layout anyone will see from the reel.[1]

Every screenshot goes to a separate agent with the same seven questions, never to the session that wrote the film. Every defect it reports has to carry the exact action, the expected behaviour, the actual behaviour and the file it can be seen in. "Looks a bit off" does not count. If no defect is found, the report says so without claiming perfection.[1]

The last step is the one that catches the most: every hardware figure the page states is checked against NVIDIA's own documentation. The DGX GB200 hardware guide gives the rack as "18x 1RU compute trays, each with 2 Grace CPUs and 4 Blackwell GPUs," nine NVLink switch trays with two NVSwitches each, and "six air-cooled 5.5kW PSUs in eight power shelves" feeding a busbar at a "nominal 50V-51V DC."[3] The product page adds the headline: 36 Grace CPUs, 72 Blackwell GPUs, 130 terabytes per second across the NVLink domain.[4]

Both files got every one of those counts right. Where they differed was in what they volunteered beyond the documentation. The Fable file states 5,000-plus cables, about 120 kilowatts, about 1.36 tonnes and 14.4 terabytes per second per switch tray, none of which appears on the pages that were read, so none of it was narrated as fact. The GPT-6 Pro file stayed closer to the guide, and linked it in its own interface.[1] That is a real difference between the two outputs, and it is a difference in citation discipline, not in intelligence.

Fig. 04 ·

what came back, as observations

Fable 5.1 in Claude Code. One file of 40,272 bytes, three.js 0.160.0 from a CDN, zero console errors, zero failed requests. A full-viewport canvas with HUD panels, and a page that starts exploding itself about a second after load. Four of the five scripted desktop clicks hit a named part. Two reproducible defects: at full explode the "Grace CPU ×36" label lands on top of "Blackwell GPU ×72," and in portrait the exploded rack runs off the left edge with two labels truncated on the right.[1]

GPT-6 Pro in ChatGPT. One file of 51,370 bytes, three.js 0.169.0, zero console errors, zero failed requests. A page layout with a sidebar, an inspector panel and a canvas column of roughly forty percent of the width. No clipping or overlap at either viewport. Two of the five scripted desktop clicks hit a part; the other three landed in empty space, because the exploded rack is thin inside a narrow column. That is a layout consequence, not a broken handler: the two hits and the portrait click all behaved correctly.[1]

On the identity question the record is careful in a way the film could only gesture at. ChatGPT never printed the word "Astra." The composer chip said "6 Pro," and the claim that this is the Astra model comes from secondary sources. The evaluation therefore narrates it as "GPT-6 Pro in ChatGPT" and never as a verified isolated Astra call.[1] Keep that in mind for the section after next.

Fig. 05 ·

why 549.8 versus 856 is not a race

The two numbers exist, and they are honest. The Claude Code process ran for 549.8 seconds from start to exit, which includes the command-line tool starting up and no isolated generation timer. ChatGPT's own badge said it "worked for 14m 16s," which is 856 seconds, plus or minus ten because it was bounded by our checks rather than read from a log, and it includes several web searches and sandbox steps that the other side was not allowed to do.[1]

So the shorter number belongs to a product with no tools, and the longer one to a product that went and read NVIDIA's documentation before answering. Anyone who reports "Fable was faster" from this pair is reporting the tool configuration, not the model. The protocol's editorial rule says it in one line: never assert that one is faster or deeper from a single output pair.[1]

This is the same lesson the benchmark world learned the hard way. The team behind the most widely used open evaluation harness wrote up, in 2024, "the sensitivity of models to evaluation setup, difficulty of proper comparisons across methods, and the lack of reproducibility and transparency" as the core problems of the field.[5] A single prompt with two different tool sets is that sensitivity in miniature.

And it is exactly the footnote on the number the film opens with. ARC Prize published GPT-6 Astra's ARC-AGI-3 results on 3 September. On the standard harness, which "enables a model to carry forward notes it chooses to keep with it," the best score was 62.7 percent, at maximum reasoning effort. On the provider adapter harness, which "preserves opaque reasoning state between requests and uses compaction for longer conversations, allowing the model to reuse prior work," the best score was 99.9 percent, at high effort. Same model, same task set, and the two headline figures differ in both harness and reasoning level.[2] ARC Prize calls both state of the art. The film calls the adapter a tutor, which is a joke; the honest version is that the harness is part of the result and the number is not comparable without it.

Fig. 06 ·

the model you asked for is not always the model that answers

One more thing the rig caught, three days after the film, on a different experiment. A follow-up series sends a single frozen prompt to Claude Code and to Codex ten times per level, with tools off and nothing carried between runs, and records which model actually answered. Claude Code was asked for claude-fable-5-1. On every counted run of that prompt, the answering model in the returned usage metadata was claude-opus-5: ten of ten on the level-three prompt, and five of five on the earlier smoke runs. A harmless prompt of the same length, and a one-word prompt, were answered by Fable four times out of four.[7]

The reroute is content-dependent. Why it happens is not known and is not claimed: it could be the model's own safety measures, a serving-side router, or a fallback inside the tool. What can be stated is only what the run files contain. But it changes how you read any product comparison, including the one above: the Fable run in the rack test did return claude-fable-5-1 in its metadata, and that line is in the evaluation precisely because a test that does not record the answering model has not tested the model it names.[1]

So add a step to your own rig, whatever you are testing: store the requested model and the answering model as two fields, and label the column by the second one.

Fig. 07 ·

does it earn a slot?

The rig, yes. The verdict, no, and that is the point. Nothing in this test says anything about general intelligence. Both products returned a finished-looking, working demo of a machine most people will never touch, in under a quarter of an hour, with the hardware counts right. Both also shipped one interaction defect that a scripted click sequence found in minutes. "Genuinely useful, occasionally embarrassing" is the film's verdict and it is the correct one, because the evidence does not support anything stronger in either direction.[1]

What is worth installing is the shape of the test. Freeze the prompt and hash it. Send it once, no follow-ups. Judge the first artifact, unrepaired. Run the identical scripted sequence on every output, at more than one viewport. Route the screenshots to a reader that did not write the prompt. Check every stated fact against a primary source. Record the answering model. Report elapsed time per run with what it includes, and refuse to call it a race.

None of that needs a benchmark, a leaderboard or a budget. It needs about forty-five lines of Node and the discipline to write the protocol before you see the first answer. If you only take one thing from this issue: a comparison is only as fair as the half you controlled, and the clock is usually in the other half.

Fig. 08 ·

the file

This is the equal-evaluation harness, condensed from the 129-line script that produced the observations above. It serves one returned index.html from a local port, opens it in headless Chrome with software WebGL so it runs on a machine with no GPU, records console errors, page errors and failed requests, then runs the same slider, drag and click sequence at a desktop and a portrait viewport, screenshotting each step and writing an eval.json beside the images. Run it once per output and hand the two folders to whoever is judging. The one dependency is puppeteer.

What was cut for length: the hash of the input file in the report, the body-text capture per step, and the click-miss diagnostics. The full version lives in the film's data folder, linked from the source page.[1]

// evaluate-output.mjs — the same scripted sequence for every returned file.
// Usage: node evaluate-output.mjs --html path/to/index.html --out eval-dir
import fs from 'node:fs';
import path from 'node:path';
import http from 'node:http';
import puppeteer from 'puppeteer';

const a = Object.fromEntries(process.argv.slice(2).map((x, i, r) => x.startsWith('--') ? [x.slice(2), r[i + 1]] : []).filter(Boolean));
const html = fs.readFileSync(path.resolve(a.html));
const out = path.resolve(a.out); fs.mkdirSync(out, {recursive: true});

// Serve the file from a real origin so CDN imports and importmaps behave.
const server = http.createServer((q, s) => { s.writeHead(200, {'content-type': 'text/html; charset=utf-8'}); s.end(html); });
await new Promise(r => server.listen(0, '127.0.0.1', r));
const url = `http://127.0.0.1:${server.address().port}/index.html`;

const report = {evaluatedUtc: new Date().toISOString(), steps: [], consoleErrors: [], pageErrors: [], failedRequests: []};
const browser = await puppeteer.launch({headless: 'new', args: ['--no-sandbox', '--use-gl=angle', '--use-angle=swiftshader', '--enable-unsafe-swiftshader', '--hide-scrollbars']});
const page = await browser.newPage();
page.on('console', m => { if (m.type() === 'error') report.consoleErrors.push(m.text().slice(0, 500)); });
page.on('pageerror', e => report.pageErrors.push(String(e).slice(0, 500)));
page.on('requestfailed', r => report.failedRequests.push({url: r.url(), reason: r.failure()?.errorText}));

const sleep = ms => new Promise(r => setTimeout(r, ms));
let n = 0;
const shot = async (name) => { n += 1; const file = `${String(n).padStart(2, '0')}-${name}.png`; await page.screenshot({path: path.join(out, file)}); report.steps.push({step: n, name, file}); };
const box = () => page.evaluate(() => { const c = document.querySelector('canvas'); if (!c) return null; const r = c.getBoundingClientRect(); return {x: r.x, y: r.y, w: r.width, h: r.height}; });
// Set the range input the way a user would: native setter + input/change events.
const slider = (f) => page.evaluate((f) => { const s = document.querySelector('input[type=range]'); if (!s) return null; const min = +s.min || 0, max = +s.max || 100; Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(s, String(min + (max - min) * f)); s.dispatchEvent(new Event('input', {bubbles: true})); s.dispatchEvent(new Event('change', {bubbles: true})); return s.value; }, f);
const drag = async (dx) => { const c = await box(); if (!c) return; const x = c.x + c.w / 2, y = c.y + c.h / 2; await page.mouse.move(x, y); await page.mouse.down(); for (let i = 1; i <= 20; i++) { await page.mouse.move(x + dx * i / 20, y); await sleep(15); } await page.mouse.up(); await sleep(1200); };
const click = async (fx, fy, name) => { const c = await box(); if (!c) return; await page.mouse.click(c.x + c.w * fx, c.y + c.h * fy); await sleep(900); await shot(name); };

async function run(tag, viewport) {
  await page.setViewport(viewport);
  await page.goto(url, {waitUntil: 'networkidle2', timeout: 60000});
  await sleep(5000); await shot(`${tag}-load`);
  if (viewport.width > viewport.height) {
    await slider(0.5); await sleep(1500); await shot(`${tag}-explode-mid`);
    await slider(1.0); await sleep(1500); await shot(`${tag}-explode-max`);
    await slider(0.0); await sleep(1500); await shot(`${tag}-assembled`);
    await drag(320); await shot(`${tag}-orbit-side`);
    await drag(320); await shot(`${tag}-orbit-rear`);
    await drag(-640); await shot(`${tag}-orbit-return`);
    await slider(1.0); await sleep(1500);
    for (const [fx, fy, name] of [[0.5, 0.35, 'upper'], [0.5, 0.5, 'centre'], [0.5, 0.7, 'lower'], [0.35, 0.5, 'left'], [0.65, 0.5, 'right']]) await click(fx, fy, `${tag}-click-${name}`);
  } else {
    await slider(1.0); await sleep(1500); await shot(`${tag}-explode-max`);
    await click(0.5, 0.5, `${tag}-click-centre`);
  }
}

await run('desktop', {width: 1440, height: 900, deviceScaleFactor: 1});
await run('portrait', {width: 1080, height: 1920, deviceScaleFactor: 1});
await browser.close(); server.close();
fs.writeFileSync(path.join(out, 'eval.json'), JSON.stringify(report, null, 2));
console.log(`${report.steps.length} steps; errors=${report.consoleErrors.length + report.pageErrors.length} failedRequests=${report.failedRequests.length}`);

Two habits make it fair rather than merely repeatable. Write the sequence down before you have seen any output, so a step cannot be added because one file happens to fail it. And keep the screenshots out of the context that wrote the prompt: hand the folder to a separate reader with a fixed list of questions, and require every reported defect to name the action and the file it is visible in.
