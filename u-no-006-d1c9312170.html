Only what you asked for.

The CLAUDE.md file from the video, the one-line install, what it changed when we tested it, and a kit to rerun our test yourself. The file is andrej-karpathy-skills: four rules, built from Andrej Karpathy's notes on how coding models fail, that Claude Code reads at the start of every session.

terminal · your project folder
curl -o CLAUDE.md https://raw.githubusercontent.com/multica-ai/andrej-karpathy-skills/main/CLAUDE.md

This line replaces any CLAUDE.md already in the folder. Already have one? Use the append line in the install section.

Codex and other agents

The repo ships no AGENTS.md (proposals to add one are open, unmerged). Codex reads AGENTS.md from your project root, and from ~/.codex/AGENTS.md for every project, so save the same text under that name. CURSOR.md says the same for any tool with one root instruction file.

terminal
curl -o AGENTS.md https://raw.githubusercontent.com/multica-ai/andrej-karpathy-skills/main/CLAUDE.md

The plugin route, and how it differs

The README recommends a Claude Code plugin. Inside Claude Code:

inside Claude Code
/plugin marketplace add forrestchang/andrej-karpathy-skills
/plugin install andrej-karpathy-skills@karpathy-skills

Know what you get: the plugin installs the rules as a skill, not as an always-on file. Anthropic's docs say Claude sees a skill's name and description every session but "only reads the full file when the task calls for it", and Claude Code's own plugin validator warns that a CLAUDE.md at a plugin's root "is not loaded as project context". If you want the four rules in front of Claude every session, use one of the file routes above. These are the README's commands word for word (the repo has since moved to multica-ai; the old name redirects). We validated the plugin's manifest but did not run the install end to end.

CLAUDE.md · 65 lines
# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

Published at github.com/multica-ai/andrej-karpathy-skills (formerly forrestchang/andrej-karpathy-skills) · download the file

On 2026-11-11 we ran Claude Code (2.1.322) unattended with claude -p --model sonnet on a 15-line cart.py and gave it one request: "Add discount code support to total(). The code SAVE10 takes 10% off." Four runs without the file, four with it, everything else the same.

The limits

One model, one toy repo, four runs a side on the main request. Rule 4 changed nothing here: Claude already ran the tests and reported the result truthfully in all 14 runs, with or without the file. The with-file runs loaded the file through --append-system-prompt-file, with this machine's own CLAUDE.md files switched off in both arms; that stands in for the project-root install, it is not the install itself. It shows what the file did on this task, not what it will do on yours.

Rerun our test.

The same four files we used, plus the script. Needs Claude Code logged in, git, Python and a POSIX shell. Each run is capped at $0.50; ours cost $0.037 to $0.055 each.

The kit

README.md (the steps and what to look for) · run.sh · cart.py · test_cart.py · CLAUDE.md

Put all five in one folder, then from that folder:

terminal · the kit folder
chmod +x run.sh
./run.sh without 1 && ./run.sh with 1

Then compare runs/without-1.diff with runs/with-1.diff. Look for an extra codes table without the file, and a single check with it. Pass your own request as a third argument, for example ./run.sh with 2 "Add input validation to total().".

Fig. 06 ·

Where the rules come from.

The file is built from his notes: a post Andrej Karpathy published on X on 2026-01-26, "A few random notes from claude coding quite a bit last few weeks." Rules 1 to 3 come from these lines, word for word:

"The most common category is that the models make wrong assumptions on your behalf and just run along with them without checking."
"They also really like to overcomplicate code and APIs, they bloat abstractions, they don't clean up dead code after themselves, etc."
"They still sometimes change/remove comments and code they don't like or don't sufficiently understand as side effects, even if it is orthogonal to the task at hand."

Rule 4 comes from the same post: "Don't tell it what to do, give it success criteria and watch it go. Get it to write tests first and then pass them."

And his own caveat: all of this happens "despite a few simple attempts to fix it via instructions in CLAUDE . md". So treat the file as a good attempt, not a proven fix: our test is one small check of it.

Fig. 07 ·

Five questions.

Will it overwrite my CLAUDE.md?

The curl -o line does. The append line does not; the file itself says "Merge with project-specific instructions as needed."

One project, every project, or the plugin?

./CLAUDE.md is this project, always loaded; ~/.claude/CLAUDE.md is every project, always loaded; the plugin is a skill Claude reads when it judges the task relevant (Anthropic's memory and plugin docs).

Will it make Claude slower, or ask too much?

The file says it will lean that way: "bias toward caution over speed". In unattended claude -p runs nobody answers a question, and an open pull request on the repo (#169) flags that "stop and ask" can stall them; for those, tell Claude to note its assumptions and carry on. No independent speed measurement exists that we could find.

Do newer models still need it?

Less than older ones. Anthropic's July 2026 post on context engineering for Claude 5 models says "newer models have better judgement and can handle these decisions well without explicit rules". An archived issue on the repo (#65) points out that Claude Code's own instructions already say "Don't add features, refactor, or introduce abstractions beyond what the task requires." Our test still saw a difference on rule 2, on today's Sonnet.

What else should go in the same file?

Your test command. Anthropic's best-practices page: "the single most useful line in your CLAUDE.md is the command that runs it." It gives rule 4, loop until verified, something to run.
