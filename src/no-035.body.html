1. The model never makes the call

This is the whole misconception in one line. People picture the model reaching out and hitting Slack's API directly, with MCP as some new kind of REST. That is not what happens, and the spec is explicit about it:

MODEL      decides which tool to run
   ↓
YOUR APP   intercepts the call and routes it
   ↓
MCP SERVER executes it
   ↓
SLACK API  the same endpoint your code always called
   ↑
   └─────── the answer goes back as text

In the documentation's own words: the AI application "intercepts the tool call, routes it to the appropriate MCP server, executes it, and returns the results back to the LLM." Your API is at the end of that chain, unchanged, being called the way it always was.

2. A tool is a thing that calls your API

If you want the shortest possible proof that MCP is not a replacement, read what the spec says a tool actually does. Tools are "executable functions that AI applications can invoke to perform actions (e.g., file operations, API calls, database queries)".

An API call is listed as an example of a thing a tool does. A protocol whose primitives are defined in terms of calling APIs is not a protocol that removes them. MCP describes itself as "a USB-C port for AI applications" — a socket in front of the things you already have, not a replacement for them.

3. Five apps, ten services, fifty pieces of glue

Say you run five applications and each needs to talk to ten services — Slack, Gmail, Jira, Notion, your own database, and so on. For every pair, somebody writes the same four things: the authentication, the call, the error handling, the retries.

5 apps  ×  10 services   =   50 integrations, written by hand

That number is a product. Add one app and it grows by ten. Add one service and it grows by five. This is the thing that actually hurts, and it is not the API's fault.

4. Fifteen, because it stops multiplying

MCP's architecture is one server per service, and — quoting the spec — an application creates "one MCP client for each MCP server" it connects to. So the count stops being a product and becomes a sum:

10 servers  +  5 clients   =   15

Same five apps, same ten services, same APIs behind them. The APIs did not go anywhere. The glue went from a grid to two edges of it, which is the entire pitch — and it is why the film shows the middle of the grid disappearing rather than the whole thing.

Worth being precise: this is the shape of the argument, not a benchmark. Your real number depends on how many of those servers already exist (thousands do) versus how many you write yourself.

5. They deleted the one feature that went around your API

MCP had a client primitive called Sampling. It let a server ask the host application for a model completion — so a server author could get LLM output without ever touching a provider API or shipping an SDK. It was the single place in the protocol where "MCP instead of the API" was literally true.

As of protocol version 2026-07-28 it is deprecated. The guidance underneath it reads: "New implementations should integrate directly with LLM provider APIs."

Read that again in the context of the argument. The protocol removed its one API-bypassing feature and told implementers to call the API directly. The correction this issue makes is one the specification makes about itself.

Logging was deprecated in the same version, with implementers pointed at stderr or OpenTelemetry — again, the existing tool rather than a protocol-shaped substitute for it.

8. Three numbers we found and did not use

Because leaving them out silently would be the same trick everyone else is running. Each of these is floating around and each failed our own check:

"9,652 servers in the official registry." A blog's figure, not the registry's. We walked the registry API ourselves and stopped at 20,000 because that was our own page limit — not the end of the data. A number that stops where your loop stopped is not a count, so we printed neither.

"100,958 servers across all registries." An aggregate of aggregates. No way to check it at source.

"97M downloads." Widely repeated, no primary reference we could find.

None of these would have changed the argument. That is exactly why using them would have been indefensible.
