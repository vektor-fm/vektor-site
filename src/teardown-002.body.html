Fig. 01 ·

the one claim with a control next to it

Two numbers went down and one stayed still. The one that stayed still is the reason the other two are worth reading — a tool that halves your token bill by answering worse has not saved you anything, it has just failed more cheaply.[1]

Fig. 02 ·

a correction, first

The 60-second version of this, which went out on Instagram on 16 August, says of the repo it recommends: "It's so good they put the benchmark in the repo. Nobody else in this category did that."

That second sentence does not survive a careful read. Going back through the other four repositories at source on 17 August, two of them do publish measurements in the repo: token-reducer ships a BENCHMARK.md with a full methodology section,[7] and claude_memory ships an entire benchmark suite called DevMemBench that measures retrieval quality and uplift over a hand-written CLAUDE.md baseline.[9] Saying nobody else did that was wrong, and it was wrong in the direction that flattered the recommendation.

The claim that does hold is narrower and, I think, more useful: only one of the five measured its saving on a task set it did not write itself, and reported an answer-quality number beside the saving. That is the distinction the rest of this issue is about.

Fig. 03 ·

five claims, and what is behind each

Star counts and licence read from the GitHub API on 17 August 2026. Every claim below is quoted from the repository's own documentation, read the same day. None of these numbers has been independently reproduced — including the one this issue ends up recommending.

zilliztech/claude-context · 12,405 ★ · MIT

Claims "~40% token reduction under the condition of equivalent retrieval quality".[3] Behind it: 30 instances drawn from Princeton NLP's SWE-bench Verified, filtered to 15–60 minute problems with exactly two file modifications, each method run three times independently for six runs total, on GPT-4o-mini. Result: 73,373 → 44,449 tokens (−39.4%), 8.3 → 5.3 tool calls (−36.3%), F1 0.40 either way.[1]

SWE-bench Verified is a 500-instance, human-validated subset of SWE-bench built from real issue and pull-request pairs in Python repositories.[2] Thirty of five hundred is a small slice, and the filter selects for the easier end of it. But it is a public task set with a known provenance, and the tool's authors did not get to choose what the questions were.

Madhan230205/token-reducer · 43 ★

Claims "Cut Claude API costs by 90%+", and elsewhere "Reduces tokens by 90-98%".[7] Behind it: a BENCHMARK.md reporting 98.9% token savings — measured on the token-reducer codebase itself, 51 files indexed, 5 queries benchmarked.

Two things to notice. The corpus is the tool's own repository, so the questions and the material were both chosen by the same person. And the same summary table reports a "5.83x average compression ratio" beside the 98.9% saving; 5.83x is roughly an 83% reduction, and the document does not say how the two relate. They may well measure different things. I have not established that they contradict each other — only that a reader cannot reconcile them from what is published.

lucasrosati/claude-code-memory-setup · 937 ★

Claims "71.5x fewer tokens per session" in the title.[8] Behind it: a "Real Results" table from one React and Supabase project of 126 TypeScript files, which reports "Token reduction per query: 499x". The two headline multipliers, 71.5x and 499x, are different numbers for different units, and no run count is given for either.

The underlying comparison is an arithmetic one — re-reading roughly 40 files at about 20,000 tokens, versus querying one graph at about 280 tokens. That is a reasonable estimate of a best case. It is not a measurement of what happened across a set of tasks.

codenamev/claude_memory · 24 ★

Claims "10x reduction in memory queries with progressive disclosure".[9] Behind it: DevMemBench, a benchmark suite shipped inside the repo that measures retrieval quality, truth-maintenance accuracy, negative-fact harm, and uplift over a hand-written CLAUDE.md baseline. Offline runs are local and free; the end-to-end runs cost roughly $5–15 of real Claude usage per full run, which the repo states plainly.

This is the most self-aware documentation in the group, and the harm benchmark is something nobody else in the category attempts. What it does not do is tie the headline "10x" to a specific published run, so the claim and the benchmark sit next to each other rather than the second supporting the first.

apolloraines/ClaudeSlim

Claims, according to third-party listicles and a search-indexed description, 60–85% savings or 6.5x. Behind it: the GitHub API returns HTTP 404 for the repository, on 14 August and again on 17 August 2026. Deleted, renamed and made private are all consistent with that; what is verified is only that it is not there.

Fig. 04 ·

it is not semantic search instead of grep

The framing everyone repeats is that these tools swap keyword search for semantic search, so the agent finds the right file by meaning instead of by string match. The recommended one does not do that. Its own README describes "hybrid search (BM25 + dense vector)" — BM25 being the classic keyword ranking function.[3] Keyword matching did not get replaced. It got an index built next to it, and a second retriever voting alongside it.

That detail matters more than it sounds, because embeddings alone are not clearly better at this. Anthropic's own retrieval work measured a standard embeddings-only setup failing to surface the relevant chunk in the top twenty 5.7% of the time. Adding contextualisation to the chunks brought that to 3.7%; adding a contextual BM25 pass on top brought it to 2.9%; adding a reranking step brought it to 1.9%.[4] The single largest structural gain in that sequence comes from keeping keyword search in the loop, not from dropping it.

So the honest description of what you are buying is not "the agent understands your code now". It is: the expensive part of an agentic search — reading whole files into context to find out whether they are relevant — happens once, at index time, instead of on every question. The saving is the re-reading, and that is exactly what the token and tool-call numbers in Fig. 01 show going down.

One number in that evaluation deserves saying out loud: F1 0.40, for both arms. Retrieval quality is equal, and in absolute terms it is not good — most of what should have been retrieved was not, either way. The claim is that indexing costs you nothing in quality, not that it makes retrieval good.

Fig. 05 ·

what it actually costs

The install the documentation leads with wants two accounts:[3]

claude mcp add claude-context \
  -e OPENAI_API_KEY=sk-your-openai-api-key \
  -e MILVUS_ADDRESS=your-zilliz-cloud-public-endpoint \
  -e MILVUS_TOKEN=your-zilliz-cloud-api-key \
  -- npx @zilliz/claude-context-mcp@latest

Which is the obvious objection to the whole category: you are spending someone else's tokens to save your own, and you are shipping your codebase to a vector database you do not run.

Except that neither of those two credentials is actually mandatory. The MCP package documents four embedding providers — OpenAI, VoyageAI, Gemini and Ollama — and the Ollama path runs the embedding model on your own machine: "Ollama allows you to run embeddings locally without sending data to external services." The same document lists the vector store as "Milvus vector database (local or cloud)".[5] Both halves have a local option, and the setup that sends nothing anywhere is three lines of configuration:

EMBEDDING_PROVIDER=Ollama
EMBEDDING_MODEL=nomic-embed-text
OLLAMA_HOST=http://127.0.0.1:11434

If you do take the default cloud path, the embedding spend is smaller than the objection implies. The default model is text-embedding-3-small, priced at $0.02 per million tokens.[6] Indexing a million tokens of source code once therefore costs about two cents — arithmetic on that price, not a measured bill, and it excludes re-indexing as the code changes. The meaningful cost of the cloud path is not the money. It is that your code leaves your machine.

Fig. 06 ·

where it breaks

The evaluation is the vendor's own

They ran it, on their tool, and chose the 30 instances and the filter. That is not independence and the repo does not claim it is. It is still a public dataset and a published method, which is the whole reason this issue points at it rather than at a bigger number.

It was measured on GPT-4o-mini, not on Claude

Chosen "for cost-effective considerations".[1] A cheaper model with a smaller working style is exactly the case where re-reading files hurts most, so the saving on a stronger model is an open question. Nobody has published that run.

Thirty instances, filtered to the easy end

15–60 minute problems with exactly two file modifications, from a 500-instance set.[1][2] A sprawling ten-file refactor is not what was tested, and that is the case where retrieval matters most.

An index is a thing that goes stale

Everything above measures a static repository. Whatever it costs to keep the index current against a branch you are actively changing is not in the published evaluation, and it is the number I would most want before adopting this on a busy codebase.

The repository has been quiet

The GitHub API reports the last push as 14 July 2026, read on 17 August 2026 — a month without a commit. Not damning for a tool that works, worth knowing before you build a workflow on it.

Fig. 07 ·

does it earn a slot?

Conditionally, and the condition is your repo size. If your codebase is small enough that the agent can grep and read its way around it in a few calls, an index is machinery you are maintaining for a saving you will not notice. The measured gain was three fewer tool calls on a two-file bug fix. Below some size, that is noise.

If your repo is large enough that "which file is this even in" routinely burns tens of thousands of tokens before any work starts, then a persistent hybrid index is the right shape of fix, and this is the one implementation in the category that has published a number you can argue with. Install it on the local path — Ollama embeddings, local Milvus — and you have given up nothing but disk.

If you only take one thing from this issue, take the test rather than the tool: a token-saving claim without a quality number beside it is not a result. Any tool can cut your token usage to zero by answering nothing. Four of the five repositories here report what they saved. One reports what it cost to save it.
