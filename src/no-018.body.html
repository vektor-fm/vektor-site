bottle-the-brain.txt · one run, your smartest model
You are the smartest model I have access to, and this is your one run
on this codebase. First explore the repository — entry points, configs,
folder layout, tests, dependency manifests — then write THREE files at
the repo root. Every claim must cite a real file path; if you did not
open it, do not assert it. No generic advice anywhere.

FILE 1 — 01-overview.md. What this app is, in one paragraph a new
developer could repeat. The major pieces and how data flows between
them, entry to exit. WHY the architecture is shaped this way — the
constraint or trade-off behind each big decision, not just what exists.
End with the load-bearing files: path + what breaks if it changes.

FILE 2 — 02-gaps.md. Audit the codebase for weaknesses: tech debt,
untested paths, fragile edges, swallowed errors, security holes
(unvalidated input, secrets in code, injection). Write each as a
workable ticket — severity P0/P1/P2, file:line, what is wrong, why it
matters, the concrete fix — ordered by risk. A ticket that could apply
to any codebase is a failed ticket.

FILE 3 — CLAUDE.md. Upgrade the existing one if present; keep what is
still true. Standing orders for a fresh session: the exact build, test
and run commands (verified against the config files, not guessed); the
conventions this codebase actually follows; the never/always rules you
would give a junior; the gotchas you hit while exploring — what looks
wrong but is intentional, what looks fine but bites.

Quality bar: a cheaper model reading only these three files should
start its next session knowing what you know right now.

File 1 · 01-overview.md know

What the app is — and why.

A cheaper model isn't just less clever — it starts every session blind: no memory of your codebase, no record of how the pieces fit. The overview is the map the smart model draws once. The why-section matters most: architecture described without its trade-offs reads like a directory listing, and the next session will "improve" a decision it never understood.

01-overview.md · the skeleton
# 01-overview.md — the map

## Purpose
One paragraph: what the app does, who it serves, the job it is hired for.

## Architecture
Each major piece — name, path, one line on its job.

## Data flow
How one request/job moves through the system, entry to exit.

## Key decisions
Why it is built this way: each decision + the constraint/trade-off behind it.

## Conventions
The naming, layout and patterns a new session must follow to fit in.
purpose · architecture · data flow · key decisions · conventions
File 2 · 02-gaps.md audit

Every weakness, as tickets.

Point the smart model at the whole codebase and make it list what's wrong: tech debt, untested paths, fragile edges, security holes. The format is the trick — severity-tagged tickets with a file:line and a concrete fix, so the cheaper model doesn't have to judge anything. The expensive brain finds the problems; the cheap one works the list, ticket by ticket.

02-gaps.md · the skeleton
# 02-gaps.md — the honest audit

Ordered by risk. One ticket per weakness — each workable as-is.

## P0 · fix before shipping anything else
### [P0] Short title of the weakness
- Where: path/to/file.ext:line
- What: the weakness, one or two lines
- Why it matters: the failure it will cause
- Fix: the concrete change

## P1 · fix this week
Same ticket format. Untested critical paths and fragile edges live here.

## P2 · track it
Same ticket format. Debt that slows you down but won't break production.
P0/P1/P2 · file:line · why it matters · the concrete fix
File 3 · CLAUDE.md orders

Standing orders, every session.

Claude Code reads CLAUDE.md at the start of every session — so load it with everything the smart model learned: the exact commands, the real conventions, the never/always rules, the gotchas. This isn't a prompt trick you paste each time. The smart model writes it once, and every cheap session after starts from it — its logic, its standards, already on the page.

CLAUDE.md · the skeleton
# CLAUDE.md — standing orders (read at every session start)

## What this is
One line on the project + pointers to 01-overview.md and 02-gaps.md.

## Commands
Build / test / run / lint — exact commands, copy-paste ready.

## Style
The conventions actually used here, not aspirations.

## Laws
The never/always rules: "never edit X by hand", "always run tests before Y".

## Gotchas
What looks wrong but is intentional; what looks fine but bites.
