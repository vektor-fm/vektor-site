The Teardown · 007

Find dead code
before deleting it.

Give Claude a daily maintenance job whose result you can check. Start with a report: a candidate, the evidence and what still needs checking.

Fig. 01 ·

start with evidence

Boris Cherny described Claude running a daily routine to find dead code and propose its removal. That is his account of Anthropic's maintenance work, not evidence that this prompt will work in your repository.[3]

Anthropic offers cloud routines that can run a saved prompt on a schedule.[1] For a first attempt, I'd ask for a candidate and the evidence behind it. Review that report before deciding whether anything should go.

This is a new, untested Vektor prompt. It does not reproduce Anthropic's internal configuration. Run duration, time saved and success rate: no current number.

Fig. 02 ·

the complete prompt

Start with a small repository you know. Paste the whole prompt, including the limits and the instruction for an empty result.

Inspect this repository's default branch for one function
that may no longer be used. Read and report only.
Do not edit files, install tools, run project scripts,
commit, push, open pull requests or contact services.

Search the repository for references to the candidate.
Check exports, configuration and dynamic loading paths.
Do not treat an empty text search as proof of disuse.

Return a report in this session with:
Candidate: file path and function name.
Evidence: searches performed and relevant file locations.
Uncertainty: anything you could not establish.
Next check: how a maintainer should verify usage.

If nothing is convincing, say "No convincing candidate"
and explain what you inspected. Do not invent a finding.

The candidate gives you something specific to inspect. The evidence should make the reasoning traceable. The uncertainty and next check tell you what remains unresolved. An empty report is acceptable; finding something to delete is not the acceptance test.

Fig. 03 ·

set it up

The setup below follows Anthropic's documentation, checked on 2026-11-01.[2] It is a recipe to try, not a measured setup-time claim.

  1. Check access. You need an eligible paid Claude plan, cloud sessions enabled and GitHub access.
  2. Create the task on the web. Open Scheduled tasks, sometimes labelled Routines. Choose New task or New routine, then Set up manually if offered. Name it Daily dead-code check and paste the complete prompt above.
  3. Set its scope. Select your repository, cloud environment and model. Remove all connectors for this job.
  4. Choose a daily schedule. Pick 9:07, not 9:00 local time: runs set on the hour can start several minutes late. This does not guarantee an exact start.
  5. Inspect a first run. Create it, click Run now, then open the run from History.

Terminal shortcut: in a local Claude Code session signed in to claude.ai, type /schedule to create the same scheduled task through a conversation; supply the prompt and settings above. Use this instead of web creation, so you do not create a duplicate.[2]

Fig. 04 ·

review the report

Use this checklist before accepting a candidate. These are review questions, not results from a run.

  • Locate it. Open the reported file and function. Check that the report describes the code you are reviewing.
  • Follow the evidence. Inspect the searches and referenced file locations. A conclusion without a traceable search is not enough to act on.
  • Challenge an empty search. Ask whether exports, configuration, dynamic loading or callers outside this repository could explain the missing references. Keep unresolved usage questions in the report.
  • Make the next check concrete. Ask what a maintainer would inspect or test before proposing a deletion. This report-only prompt forbids running project scripts; do not mistake its report for a test result.
  • Accept no finding. If it says there is no convincing candidate, read what it inspected. Do not ask it to invent one to make the run look productive.

Keep the routine only if its report helps you make a decision. If the evidence is vague, narrow the prompt to a folder you know and try again. Any later change to code is a separate decision.

Fig. 05 ·

what remains untested

Read-only wording is an instruction, not a permissions lock. Removing connectors does not prove that the remaining environment cannot write. Review what access you grant before creating the task.
