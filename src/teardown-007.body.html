The Teardown · 007

Delete your dead code
every morning.

Boris Cherny, who built Claude Code, says one of Anthropic's daily routines is a single sentence that deletes their dead code. The feature is public: Claude Code calls it scheduled tasks, formerly routines. Here is my version of that prompt with its guardrails, the ten-minute setup from the docs, and the one thing static analysis cannot see.

Fig. 01 ·

what he said

At YC's Startup School, Boris Cherny described a Slack channel where Anthropic had Claude start "a bunch of different routines" to maintain its own code base, for the CLI, iOS, Android and desktop apps. Of the first one he said "one routine is clean up dead code", that "this is a single prompt", and that "it's one sentence." Claude runs it every day, it looks for dead code "using static and dynamic analysis", and "it'll put up pull requests every day to delete the dead code."[1]

His prompt is not public, and neither is how Anthropic's internal routines are configured. What is public is the feature: a scheduled task is a saved Claude Code configuration, a prompt plus one or more repositories and connectors, that runs on Anthropic-managed cloud infrastructure "so they keep working when your laptop is closed".[2]

Fig. 02 ·

the dead code prompt

My version, written from his description. The first sentence is the job. The rest are guardrails: the docs say a scheduled task runs autonomously, so the prompt must be self-contained and explicit about what success looks like.[2]

Find code in this repository that nothing uses any more:
unreferenced functions, files, exports and feature flags.
Use static analysis, then confirm with the build and the tests.
Skip anything that is a public API, is loaded by name from
config, or is used by another repository.
Delete at most ten items, run the tests, and push one branch
with one line per item saying why it is safe to remove.
If you are unsure about an item, leave it and say so.

Why each guardrail is there. "Confirm with the build and the tests" is the cheap version of his dynamic analysis. "At most ten items" keeps the diff small enough to read in one sitting. The skip list covers the code static analysis cannot see (Fig. 04). "Leave it and say so" gives the run a way to finish without deleting something it guessed about.

Fig. 03 ·

set it up in ten minutes
  1. Sign in with a claude.ai plan. Scheduled tasks are available on Pro, Max, Ultra, Team and Enterprise. /schedule needs a claude.ai subscription login: with a Console API key or a cloud provider login it does not work, and an ANTHROPIC_API_KEY set in your shell takes precedence over the claude.ai login.[2]
  2. Create the task. In the repo, type /schedule daily dead code cleanup at 9:07am. Claude asks follow-up questions about the schedule, repositories and prompt before saving; paste the prompt when it asks. The command also answers to /routines. The same task can be made on the web at claude.ai/code/routines.[2]
  3. Pick 9:07, not 9:00. A run scheduled exactly on the hour can start several minutes late. Preset times are in your local time zone; a bare cron expression is in UTC, and nothing more frequent than hourly is accepted.[2]
  4. Run it once now. /schedule run starts a task immediately, so you read the first result today instead of tomorrow.[2]
  5. Review, then merge yourself. Each run clones the repo from its default branch and pushes its work to a branch prefixed with claude/. Open the run from the task's History, read the diff, and create the pull request from there.[2]

If GitHub access is missing, /schedule adds a setup note saying how to grant it. If a connection expires, the task skips runs for up to 72 hours and turns itself off after that.[2]

Fig. 04 ·

before you merge

Static analysis cannot see code that is called by name. A route registered as a string, a plugin loaded from a registry, a handler named in a config file, a job that another repository triggers: none of them has a reference in the code, so all of them look dead. That is why the prompt skips them, and why every deletion still gets read by a person before it merges.

Three more things the docs state. Commits and pull requests carry your GitHub user. Runs draw on your subscription usage the same way interactive sessions do, and scheduled runs are capped at 100 per hour per account. And the feature is in research preview, so behaviour, limits and the API may change.[2]

What we have not done: we have not created this task or run this exact prompt on a repository. The setup steps are the docs' own; the prompt is ours and untested. If you run it, reply and tell me what the first pull request looked like.

Fig. 05 ·

all five routines, my versions

He named five routines in the talk.[1] These are my one-job versions, first published with the film.[3] Each one goes into its own scheduled task, with the same guardrails as above added to taste.

DEAD CODE
Find code in this repository that nothing uses any more (unreferenced functions, files, exports and flags) with static analysis, and with a dynamic check where the tests or build allow it, then open one pull request that deletes it and says why each item is safe to remove.

SHIP FINISHED EXPERIMENTS
Find feature flags and experiments that are already rolled out to 100%, remove the flag and the losing branch so the winning code is simply the code, and open one pull request per experiment.

MISSING TESTS
Find the parts of this codebase with the least test coverage that matter most, write tests for one of them that pass against the current behaviour, and open a pull request with the new tests only.

USELESS TESTS
Find tests that no longer earn their place (they test nothing real, duplicate another test, or only check a mock), delete them, and open a pull request that explains each deletion in one line.

ABSTRACTION POLICE
Find places where the same idea has been built more than once in slightly different ways, pick the best version, merge the others into it without changing behaviour, and open one pull request per merge.

Start with one. A routine that does one thing gives you a pull request you can review in a few minutes, and you stay the one who merges it.
