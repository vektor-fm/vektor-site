Ten thousand files, drawn as a galaxy.

Claude Code (VS Code extension, Opus 5.5, auto mode) shallow-cloned VS Code's own repo, read src/, and wrote repo-map.html: one self-contained 1.34 MB file. Every top-level module is a cluster of glowing stars, one star per file, sized by lines of code. Imports between files flow between the clusters as animated particles, so what depends on what is visible at a glance instead of buried in an import graph nobody opens.

Hover a cluster and everything it touches lights up. Click one and the camera flies in, resolving into its individual files, each carrying one plain-English line on what that file actually does.

Every file gets a description, read from the file itself

Fly into a cluster and every star carries a one-line, plain-English description of what that file does. 1,435 of the 10,022 (14%) are pulled from the authors' own code comments; the rest are generated from what the code itself declares, its classes, its registered commands, its test suites, not from a second model pass guessing at a filename. That second pass would have cost real tokens for a marginal gain, so the page skips it: some lines read a little mechanical because of that trade, not because they're guessed.

It held up under a headless check

Run through headless Chrome on this laptop: 0 console errors, roughly 60fps steady, dipping to 50 to 57fps during the fly-in camera move into a cluster.

Fig. 04 ·

Before you run it.

What to expect, and where this does and doesn't work.

Where it runs

Built and measured in Claude Code, and the terminal, VS Code and JetBrains variants should all read the same prompt the same way since it's just one message with no tool-specific syntax. It should also work in Codex, but that's untested; we only ran it in Claude Code.

Big repos take longer

30 minutes was VS Code's src/ alone, 10,022 files and 2.8 million lines. A smaller repo will finish faster; a much bigger one will take longer, since the agent is reading the actual code to write each file's description, not sampling filenames.

The descriptions come from the code, not a second model

Don't add a step asking a model to "write each line if the comments are thin." It sounds like a quality fix but it's a token-cost problem dressed as one: it means a second full read of every file. The prompt as written already reads the code once and writes the line from what it finds there, comments where they exist, the file's own structure where they don't.
