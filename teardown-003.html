The Teardown · 003

Anthropic's playbook,
minus the AI.

Anthropic published how it actually builds software with agents. The part worth stealing is not the agents. It is that every stage ends by committing a file, which is a 1970s idea wearing new clothes, and which works whether or not the AI is any good.

////////////////////////////////////////////////////////////////////////////////////////////////

Fig. 01 ·

six stages, six commits, one edge going backwards

Every stage "ends by committing an artifact with the commit initiating the next stage."[1] The stage names are ordinary. The discipline is not: the handoff between stages is a git commit, so the chain that produced a change and the audit trail of that change are the same object. You do not maintain the second one.

Fig. 02 ·

what the document actually is

Read it end to end and the first thing you notice is what is missing: numbers. There is no productivity multiplier in it, no defect-reduction percentage, no before-and-after on cycle time. The closest it comes to a measured claim is an aside about a support workflow, and a piece of operational advice that "two or three sessions is a sensible starting point," where "the practical ceiling is how many streams one person can review properly."[1]

That is not a criticism. It is a design document, and design documents are allowed to describe a shape rather than prove a result. But it matters for how you read it, because the internet has been quoting it as though it were a results paper. It is a description of how one company has arranged its work. Treat every claim in it as a hypothesis that Anthropic finds plausible enough to run its own engineering on, which is a real signal, and not as a measurement.

The genuinely reusable idea is the file discipline. An idea becomes intent.md, described as "what is wanted, why, and under which constraints." That commit triggers spec.md. That triggers plan.md and the diff. Tests are evals woven through implementation rather than a phase at the end. Deploy produces a reviewed, merged PR. Maintain produces an incident record.[1]

And then the edge that makes it a cycle rather than a pipeline: when production breaks, the agent "writes its diagnosis as intent.md in the Stage 1: Plan format," and "from there the finding goes through the pipeline like anything else."[1] An incident does not get a special path. It gets the ordinary path, from the top.

Fig. 03 ·

the claim with the least evidence behind it

The playbook's premise, and the line everyone repeats, is that "code is no longer the bottleneck." It follows through: "build is no longer the constraint, the human-speed steps around it are," and the bottleneck therefore "moves to the steps to the left and right of the build phase. This is mainly plan, review/test, and deploy, which still run at human speed."[1]

This is the part of the document with the least evidence attached to it, and it is also the part the whole design rests on. So it is worth asking what has actually been measured.

The most careful thing anyone has run is a randomised controlled trial by METR, published July 2025. Sixteen experienced open-source developers completed 246 real tasks in mature repositories they had worked on for an average of five years. Each task was randomly assigned to allow or disallow AI tooling, which at the time meant mostly Cursor Pro with Claude 3.5 and 3.7 Sonnet. Before starting, the developers forecast that AI would cut their completion time by 24%. Afterwards, they estimated it had cut it by 20%. Measured, allowing AI increased completion time by 19%.[2]

The gap between the estimate and the measurement is the finding, more than the slowdown itself. These are not people with an axe to grind about AI. They used it, they felt faster, and the stopwatch disagreed by roughly forty percentage points. Economics and ML experts asked to predict the result were further out still, at 39% and 38% faster respectively.[2]

Three honest caveats, because this number gets swung around carelessly and I am not going to add to that. First, it measures early-2025 tooling in a specific setting: mature codebases with high quality standards, developers with deep prior context, no agentic harness of the kind the playbook describes. It is not a measurement of the playbook. Second, the authors say plainly that "the influence of experimental artifacts cannot be entirely ruled out," though they argue the effect is robust across their analyses.[2] Third, and most importantly, METR themselves have since reported that they cannot cleanly run this design any more: between 30% and 50% of developers told them they were declining to submit tasks "because they did not want to do them without AI," so the study is "systematically missing developers who have the most optimistic expectations about AI's value." Of their newer data they say it is "only very weak evidence."[3]

So the state of the evidence is genuinely unsettled, and anyone telling you otherwise in either direction is selling something. What you can say is this: "code is no longer the bottleneck" is an assertion, the one careful trial we have pointed the other way in its own setting, and the people who ran that trial now think their instrument is broken. That is a thinner foundation than the confidence around this document suggests.

Which is exactly why the file discipline is the part to take. It does not depend on the premise being true. If the agent is fast, the artifact chain is what stops the speed turning into unreviewable churn. If the agent is slow, you have lost nothing except some markdown. Google's DORA programme reached a compatible conclusion from the other end, reporting that "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses," and that the "greatest returns on AI investment come not from the tools themselves, but from a strategic focus on the underlying organizational system."[5] A chain of committed artifacts is an underlying organisational system, and it is one you can install this afternoon.

Fig. 04 ·

a skill asks, a hook refuses

The two guardrail layers get conflated constantly, including by people who have shipped both. The playbook's own formulation is the cleanest one-liner available: "A skill is an advisory control while a hook is the deterministic layer behind it." The rule that follows is the useful bit: "back any skill whose policy has to hold without exception" with a hook.[1]

It is worth checking that "deterministic" against the mechanism, because it is the kind of word that gets used loosely. It holds up, in one direction. In the Claude Code hooks reference, a PreToolUse hook that exits with status 2 blocks the tool call outright, and the documentation is explicit that this is not negotiable: "exit 2 blocks whether or not you print JSON: even a JSON permissionDecision of 'allow' can't override it."[4]

The asymmetry is the thing to internalise, and the docs state it in one sentence: "The hook can deny the call, but staying silent doesn't approve it."[4] A hook is a brake, not a steering wheel. It can stop the agent doing a specific thing with certainty. It cannot make the agent do a thing, and it cannot make a thing safe. If your policy is "never write to the production database," that is a hook and it will hold. If your policy is "prefer the repository's existing error-handling pattern," no hook can express that, and you are back to a skill and a probability.

One placement detail in the playbook is easy to miss and expensive to get wrong. A hook that asks a human for approval belongs at Stage 5, Deploy, "because an approval prompt during the build puts a person back on the critical path."[1] If you scatter approval prompts through the build stage you have rebuilt the bottleneck you were trying to remove, one dialog box at a time.

Fig. 05 ·

the one thing the agent may never do

Claude reviews pull requests against policy, and Claude also receives reviews and addresses the comments on its own PRs. But the boundary is absolute and, notably, it is not enforced by asking nicely: "the agent that wrote the code has no way to approve it," because "approval comes from a human through branch protection."[1]

That is the same design instinct as the hook. The rule that must hold without exception is not written into a prompt where a model can be talked out of it. It is written into the platform, where there is no conversation to have. Branch protection does not evaluate an argument.

What changes for the human is the altitude, not the workload: "human attention moves up a level, to whether the change does what the plan intended and whether the risk is acceptable."[1] This is the honest cost of the whole arrangement, and the playbook does not hide it. You are not reviewing less. You are reviewing differently, and against the plan.md that the same system committed three stages earlier, which is the only reason reviewing at that altitude is possible at all.

The production loop follows the same tiering logic. A deterministic script, not an agent, watches the metrics and calls the agent in when a control band is breached. The tiers are version-controlled: "at 1σ the script only logs, at 2σ it invokes Claude read-only to diagnose, and at 3σ Claude may act, though only by opening a PR into the review gate or triggering a pre-approved runbook."[1] Even at its most autonomous, at three standard deviations out, the agent's maximum privilege is to open a PR that a human still has to merge.

Fig. 06 ·

does it earn a slot?

Yes, and you should install the cheap half first. The artifact chain costs you four markdown files and a habit. You do not need agents, a monitoring tier, or any part of the premise to be true in order to get the benefit, which is that every change arrives with a written record of what was wanted and why, committed before the code existed rather than reconstructed afterwards in a PR description.

Start with intent.md alone, for one change, this week. If writing down what is wanted and under which constraints turns out to be hard, that is the finding, and it was going to bite you later at review time regardless of who or what wrote the code.

Be more sceptical of the expensive half. The autonomous production loop is a serious piece of infrastructure, and it is the part most likely to be cargo-culted by teams whose deploys are not yet boring. The tiering is good design, but it presupposes you already have control bands worth breaching, version-controlled response config, and pre-approved runbooks. If you have those, you probably did not need the playbook to tell you this. If you do not, build those first, without any AI in the picture, because an agent triggered by a metric you do not trust is a faster way to be wrong.

If you only take one thing from this issue: the audit trail is free only if the handoff is a commit. Every part of this design that works, the reviewable chain, the honest history, the incident that re-enters at Stage 1, works because the artifact is committed at the boundary rather than written up afterwards. Adopt that and you have most of the value. Adopt the agents without it and you have a faster way to produce changes nobody can review.

Fig. 07 ·

the file

The one rule this operation could not afford to have broken was no direct commits on main. It was written into the CLAUDE.md every session reads, in bold, on 2026-07-10. Over the next four days, sessions read it and committed on main twenty-one times across two repos. The hook below went in on 2026-07-13. In the fifty-eight days since, four direct commits reached main, all of them in the three hours between the file landing and the settings wiring that loads it. Before the written rule, the same four-day window held forty-eight. Source: git log origin/main --first-parent --no-merges on the two repos, read 2026-09-09. The site repo publishes straight from main and was never under the rule, so it is not counted.

This is the full file as it runs here, sanitised. The email carries a 36-line version; this one adds the git -C <path> handling for commits aimed at another repo, a Windows path fix for MSYS-style paths, and a per-repo escape hatch: a .git-flow-exempt file at a repo root opts that repo out. Save it as .claude/hooks/git-flow-guard.mjs in the folder above your repos and it covers every repo beneath, worktrees included. Node only, no dependencies.

#!/usr/bin/env node
// git-flow-guard.mjs — PreToolUse hook (Claude Code). Enforces the Git Flow
// branching law for every repo under projects/: no direct commits on
// main/master. Reads the hook JSON from stdin; if the shell command contains a
// `git commit` and the target repo's current branch is main or master, the
// commit is BLOCKED (exit 2) — unless a merge is in progress (MERGE_HEAD
// exists), which is the legitimate case of completing a release/hotfix merge
// into main. Pure Node — Windows-safe, no bash/jq.
//
// Wired from .claude/settings.json → hooks.PreToolUse (matcher "Bash|PowerShell").
import {execFileSync} from 'node:child_process';
import fs from 'node:fs';

let raw = '';
process.stdin.on('data', (d) => (raw += d));
process.stdin.on('end', () => {
  let input;
  try {
    input = JSON.parse(raw);
  } catch {
    process.exit(0);
  }
  const cmd = String(input?.tool_input?.command ?? '');
  // Only care about commands that actually run `git ... commit`
  if (!/\bgit\b[^|&;\n]*\bcommit\b/.test(cmd)) process.exit(0);

  // Resolve the repo the commit targets: prefer `git -C <path>`, else the
  // session cwd reported in the hook payload.
  let dir = input?.cwd ?? process.cwd();
  const cFlag = cmd.match(/\bgit\s+-C\s+("([^"]+)"|'([^']+)'|(\S+))/);
  if (cFlag) dir = cFlag[2] ?? cFlag[3] ?? cFlag[4];
  // Windows git.exe can't chdir to MSYS-style paths (/c/Users/...) — normalize.
  dir = String(dir).replace(/^\/([a-zA-Z])\//, '$1:/');

  const git = (args) => {
    try {
      return execFileSync('git', ['-C', dir, ...args], {
        encoding: 'utf8',
        stdio: ['ignore', 'pipe', 'ignore'],
      }).trim();
    } catch {
      return null;
    }
  };

  // Escape hatch: a repo with a .git-flow-exempt file at its root opts out
  // (a learning playground, a throwaway experiment).
  const top = git(['rev-parse', '--show-toplevel']);
  if (top && fs.existsSync(top + '/.git-flow-exempt')) process.exit(0);

  const branch = git(['rev-parse', '--abbrev-ref', 'HEAD']);
  if (branch !== 'main' && branch !== 'master') process.exit(0); // not on a protected branch (or not a repo / detached)

  // Completing a merge into main (release/hotfix flow, incl. conflict
  // resolution) is the one legitimate commit on main.
  if (git(['rev-parse', '-q', '--verify', 'MERGE_HEAD']) !== null) process.exit(0);

  console.error(
    `git-flow-guard: BLOCKED — direct commit on '${branch}' in ${dir}.\n` +
      `Git Flow law: main receives code only via merges from release/* or hotfix/* branches.\n` +
      `Do one of:\n` +
      `  • feature work → git checkout develop && git checkout -b feature/<name>\n` +
      `  • urgent prod fix → git checkout -b hotfix/<name> (from main), commit there, then merge back\n` +
      `  • release → git checkout -b release/vX.Y.Z (from develop)\n` +
      `See the git-flow skill for the full workflow.`
  );
  process.exit(2); // exit 2 = block the tool call and feed stderr back to Claude
});

Register it in the .claude/settings.json beside it. Settings are read when a session starts, so restart the session, check out main, and ask the agent to commit something. The refusal you get back is the message at the bottom of the file.

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Bash|PowerShell",
      "hooks": [{ "type": "command", "command": "node .claude/hooks/git-flow-guard.mjs" }]
    }]
  }
}

What it cannot do is the other half of the playbook's sentence. Exit 2 blocks the call, and the hooks reference is explicit that a JSON permissionDecision of allow cannot override it.[4] But the hook can only deny; staying silent does not approve anything, and it cannot make the agent write a good commit on the branch it is sent to. A brake, not a steering wheel. Put the rule that must hold in the hook, and put the reason it must hold in the prompt.
