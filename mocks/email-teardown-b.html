Five token claims,
one benchmark

Four of them measured it on their own homework.

Earlier this month I posted a 60-second film recommending a tool that cuts what Claude Code spends reading your codebase. I need to correct something in it, and the correction is more interesting than the recommendation.

The film said of the repo it recommends: "they put the benchmark in the repo. Nobody else in this category did that." Going back through the other four repositories properly, that is not true. Two of them publish measurements in the repo as well.

Here is what is actually true, and it took reading all five to see it.

The pattern

Every repo in this category publishes a number. 40%. 90%+. 71.5x. 98.9%. The numbers are not the problem. What they were measured against is.

Three of the five measured their saving on material they chose themselves. One benchmarked on its own source code with five queries; another on a single private project. That is not dishonest, but it is homework marked by the person who set it. A fourth repository has been taken down, and the API returns 404.

One measured differently. It ran 30 problems drawn from SWE-bench Verified (a public, human-validated set of real issues and pull requests from Python projects) three times per method, and published the harness.

Tokens / task 73,373 → 44,449 Tool calls 8.3 → 5.3 Answer quality F1 0.40 = 0.40unchanged

That third number is the one that matters, and it is the one nobody else reports. Any tool can cut your token bill to nothing by answering nothing. A saving is only a saving if you can see what it cost you. Here, it cost nothing measurable.

Two things the film had no room for

It is not semantic search replacing grep. The README describes hybrid search, BM25 plus dense vectors. Keyword matching stays; it gets an index built beside it. What you are actually buying is that the expensive part, reading whole files to find out whether they are relevant, happens once at index time instead of on every question.

It does not have to cost you an OpenAI key. The documented install wants OpenAI for embeddings and a hosted vector store, which is the obvious objection: spending someone else's tokens to save your own, and shipping your code off your machine. But the package documents four embedding providers including Ollama, which runs locally, and the vector store can be local too. Three lines of config and nothing leaves your laptop.

Does it earn a slot? Only if your repo is big. The measured gain was three fewer tool calls on a two-file bug fix. Below some size, that is noise you are maintaining an index for.
