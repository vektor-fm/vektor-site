Five repos promise to cut your Claude Code token bill. Exactly one of them published a measurement you can check. Here is the setup, the two things it costs you, and — the part nobody else prints — what that measurement actually says, and what it doesn't. As promised.

the setup, in order

Repository metadata read from the GitHub API on 16 August 2026. Stars move; the install line doesn't.

1. claude-context

Semantic search over your whole codebase, wired into Claude Code as an MCP server. Instead of grep reading every file that matches and pushing all of it into the context window, it reads the part that actually relates to what you asked and hands the model that. 12,405 stars. MIT licence.

claude mcp add claude-context

Repository: github.com/zilliztech/claude-context. Built by Zilliz, the company behind the Milvus vector database — which is worth knowing before you read their evaluation of their own tool, further down.

2. It is not free. Here are the two things it costs.

Every write-up we found skipped this. The tool needs an embedding model and somewhere to put the vectors, and both are yours to supply:

export OPENAI_API_KEY=sk-...
export MILVUS_ADDRESS=...

OPENAI_API_KEY — every file in your repo gets embedded, and re-embedded as it changes. That is a metered API bill that scales with how big your codebase is and how often it moves. MILVUS_ADDRESS — a Milvus or Zilliz Cloud vector store to hold them. Zilliz Cloud has a free tier; self-hosting Milvus is a service you now run.

Neither is a dealbreaker. Both are things you should know before you install it, not after.

what the evaluation actually says

Every figure below is quoted from the repository's own evaluation/README.md, read at source on 15 August 2026.

3. The numbers they published

They ran 30 instances from Princeton NLP's SWE-bench Verified dataset — real bug fixes in real repositories — twice over: once with grep, once with semantic search. Then they printed the difference.

average tokens      73,373  →  44,449     −39.4%
average tool calls     8.3  →     5.3     −36.3%
answer quality (F1)   0.40  →    0.40     comparable

28,924 tokens saved per instance. The quality row is the one that matters: a tool that cuts tokens by finding less is not a win, and their own numbers say the answers came out the same.

4. What it doesn't say — read this part

We are recommending this repo because it published a measurement, which is more than anything else in the category did. That is not the same as the measurement being independent. Four caveats, all from their own document:

They ran it on their own tool. Zilliz evaluated Zilliz. No third party has reproduced this.

n = 30. Thirty instances, filtered to 15–60 minutes of estimated difficulty and exactly two file modifications. That is a narrow, tidy slice of the work you actually do.

One model, chosen for price. GPT-4o-mini, picked in their words for cost-effectiveness. Whether the gap holds on a frontier model is untested.

Six runs, not two. The video says the benchmark was run twice — meaning the two arms, grep and search. Their document is more rigorous than that: each method was run three times independently, six runs in total. We are correcting ourselves upward here, which felt worth doing in public.

5. Where the "90%" claims come from

The reason this issue exists is that the category is full of much bigger numbers with nothing behind them. One repo advertises cutting token usage by 90%+, with a benchmark run against its own codebase — 51 files, 5 queries. Another claims up to 71.5× fewer tokens per session and gives no benchmark at all. A third, widely cited at 60–85%, returns a 404: the repository is gone.

We are not printing those repo names or their figures as if they were findings. A number with no method behind it isn't a small number or a big one — it isn't a measurement. That is the whole point of this issue.
