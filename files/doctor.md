# My CLAUDE.md, before and after /doctor

Measured on my own setup, 2026-09-23, in Claude Code 2.1.280. My rulebook is three
files Claude reads at the start of every session (a global one, a shared-projects
one, and the project's own). Together they were **494 lines**. I ran `/doctor` on
them in-session. It flagged **nine blocks** — about 27 lines, roughly 500 estimated
tokens a session (est. = chars / 4, the same rough method the tool itself uses) —
and two lines that were flat-out wrong. After the cuts: **458 lines**.

Every change below is a working-tree edit. Nothing here was force-fed into the
files automatically — `/doctor` proposes, you confirm, and it never commits on its
own.

## Why this is worth doing

On 24 July 2026, Anthropic's Thariq Shihipar wrote: **"We removed over 80% of
Claude Code's system prompt for models like Claude Opus 5 and Claude Fable 5 with
no measurable loss on our coding evaluations."** (claude.dev blog, "The new rules
of context engineering for Claude 5-generation models", 24 July 2026.) The newer
models don't need the hand-holding older rulebooks were written for. Every extra
rule is something the agent has to read and weigh before it even starts the task.

That matters because rules don't just sit there quietly. In GitHub issue
[anthropics/claude-code #15443](https://github.com/anthropics/claude-code/issues/15443)
(December 2025), a CLAUDE.md said **NEVER use `cp`**, written in three separate
places. Claude Code used `cp` anyway, overwrote a production file, and deleted an
API endpoint. Asked about it, it said: *"I read the words but didn't actually
follow them."* Codex users report the same pattern with AGENTS.md files (see
[openai/codex #6502](https://github.com/openai/codex/issues/6502)). A rule that's
buried in a long file doesn't reliably stop anything — and the fix isn't a louder
rule, it's fewer of them. Claude Code's auto memory (on by default, see
[code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)) now
saves the preferences worth keeping on its own, so a standing rulebook doesn't
have to carry them.

## The nine blocks it flagged, quoted, and why each went

`/doctor` doesn't judge a rule as "outdated" — it judges it as **derivable**:
something the agent could work out for itself by reading the repo, or something
already covered somewhere else that always loads. Here is every block it flagged,
quoted exactly, with the reason it gave.

1. **A description of the `public/` and `out/` folders.**
   > `- public/ — render assets. public/audio/<slug>/ VO + music, public/images/, etc.` / `Remotion staticFile() resolves against public/.` / `- out/ — rendered .mp4s and out/_qa/ gate artifacts (judge frames, stills).`
   Why it's safe: Claude can open the folders and look. It doesn't need to be told what's in them.

2. **"docs/, reports/, research/, ops/ hold docs, analytics and logs."**
   Same reason as above — a folder listing the agent can generate itself in one command.

3. **Four standard commands already in `package.json`.**
   `render:video`, `render:still`, `npm start`, and a typecheck script — all standard `scripts` entries, two of them pointing at a render path the project's own gate already blocks.

4. **The steps of an old, dead pipeline.**
   One line describing a path the canon already render-blocks, so the gate enforces it whether the line is there or not.

5. **A nine-line "Transitions" section** describing internal code (`buildTransition()`), where a separate automated check already enforces the same coupling, and the allowed values are already listed one section below.

6. **"The shell keeps its folder between commands."**
   The coding tool's own tool description already says this.

7. **"Don't put brand data in the engine repo."**
   It was written twice in the same file.

8. **A "gotcha" that just repeated the file's own opening section**, three lines up.

9. **"Write meaningful commit messages."**
   A generic practice the model already follows by default — flagged in the shared, always-loaded projects rulebook rather than the project-specific one.

## Two lines that were just wrong — these mattered more than the trims

`/doctor` also caught stale instructions, which is a different and more important
kind of finding than a redundant one:

- Two lines told sessions to deploy a Cloudflare Worker with a raw `wrangler
  deploy` command. The repo has a safer wrapper script that runs a check first —
  **the raw command can ship whatever code happens to be checked out**, which is
  exactly the kind of thing that breaks something live without anyone noticing
  until the report looks wrong the next morning. Fixed to point at the safe
  wrapper.
- A line said a script file was "generated by a script, never hand-edit." True
  for an old, dead pipeline only — the current pipeline authors that file by hand
  and gets it approved before anything downstream runs on it. Reworded to say
  which is which.

## What was kept on purpose

Every non-negotiable rule, every gate, every "never," every documented failure
mode with a specific fix, and anything that contradicts a tool's default
behaviour stayed untouched. `/doctor` also has a lighter-weight lane for things
outside the rulebook itself: on my own setup it flagged one plugin and fifteen
skills that had never been used once since install, and about a dozen long-term
memory notes that either repeated a rule already stated in the rulebook or were
already marked dead. Those are disabled or archived, never deleted — every one of
them can be switched back on in a single line.

## Run it yourself

**Claude Code:** type `/doctor` in a session inside your project. It reads every
CLAUDE.md that loads for that session and proposes trims — it explains its
reasoning for each one, and it edits nothing until you say go. (Needs Claude Code
2.1.206 or later; see
[code.claude.com/docs/en/commands](https://code.claude.com/docs/en/commands).)

**Codex / AGENTS.md:** there's no built-in equivalent yet, but you can ask for the
same pass. Copy this in:

```
Read every AGENTS.md file that loads for this session. For each rule in it, check
whether I could reasonably expect you to work it out yourself by reading the
code or repo, without being told. Flag any rule that is:
1. something you could already infer from the codebase,
2. redundant with another rule stated elsewhere that always loads,
3. describing a dead or legacy code path, or
4. factually stale (contradicted by what's actually in the repo).
For each one, quote the exact line and say why it's safe to cut. Leave every
non-negotiable rule, safety gate, and repo-specific gotcha alone — I only want
the derivable and the stale stuff flagged. Don't edit anything yet, just report.
```

For every rule your agent flags — in Claude Code or Codex — ask yourself one
question: does it actually need this, or is it just another speed bump?
